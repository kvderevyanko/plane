# Рабочая папка

Этот каталог (`/home/kirill/codex/plane`) — единственное место для рабочих
файлов проекта: исходного кода, данных, документации, скриптов, конфигурации,
загруженных portable-инструментов и временных материалов, которые нужны для
воспроизводимой работы.

Правила для агентов:

- Создавать и изменять файлы, каталоги, локальные окружения и загружаемые
  приложения только внутри этого каталога. Не создавать проектные каталоги в
  `~/codex`, `~/Applications`, `/opt`, `/usr/local` или других местах без
  отдельного явного разрешения пользователя.
- Хранить в репозитории всё, что потребуется после публикации на GitHub или
  переноса проекта на другую машину.
- Необязательные программы, локальные зависимости, кэши, сборочные результаты,
  учётные данные и машинно-зависимые настройки не коммитить; добавлять их в
  `.gitignore`.
- Если без локального инструмента можно обойтись, не добавлять его в проект.

## Правила LR1600 CAD

- Базовая единица всех геометрических величин — миллиметр (`mm`).
- Не менять аэродинамические параметры и материалы из `config/aircraft.yaml`
  без отдельного решения пользователя.
- Параметрическая исходная модель и конфигурация являются source of truth;
  файлы из `build/` вручную не править.
- Не добавлять компенсацию kerf в исходную CAD-геометрию. Kerf задаётся только
  на производственном этапе.
- Существенные инженерные решения документировать в `docs/`.
- Перед изменением размеров крыла пересчитывать площадь, MAC и нагрузку.
- Перед выпуском файлов для физического производства запускать автоматические
  проверки. Успешный экспорт DXF сам по себе не означает готовность к резке.

## Публикация в GitHub

- После явной просьбы пользователя создать commit самостоятельно подготовить
  нужные изменения, создать commit и сразу выполнить push в `origin` без
  дополнительного подтверждения. Исключения: пользователь явно просит только
  локальный commit, запрещает push или задаёт иной remote/branch.
- Репозиторий публичный: до commit/push проверять изменения на секреты,
  учётные данные, токены, приватные ключи и машинно-зависимые конфигурации.
  Такие данные не добавлять в Git и включать в `.gitignore`.

## Команда специализированных агентов LR1600

Project-scoped роли находятся в `.codex/agents/*.toml`; подробные инструкции
остаются в этих файлах и не дублируются здесь. Каждая роль должна явно
закреплять модель и уровень рассуждения, чтобы не наследовать алиас `gpt-5.6`,
который направляет запросы на более дорогую GPT-5.6 Sol. Базовый профиль для
LR1600 — `model = "gpt-5.6-terra"` для рабочих специалистов: он обеспечивает
инженерное качество при контролируемом расходе токенов. `aircraft-lead` и
`independent-reviewer` явно используют `model = "gpt-5.6-sol"` с `high`, но
только как редкие gatekeeper-роли для системного решения и обязательного
независимого ревью. `high` требуется для аэродинамики, прочности и авионики;
`"medium"` достаточен для CAD/laser automation. GPT-5.6 Luna не назначается
инженерным ролям. Изменять этот профиль можно только отдельным инженерным
решением.

### Экономный запуск агентов

- Сначала запускать детерминированные проверки и генераторы; не вызывать LLM,
  если они уже дают проверяемый ответ. Проверка профилей:
  `./tools/check-agent-profiles.sh`.
- На одну ограниченную подзадачу назначать одного owning-специалиста; не
  запускать несколько ролей для повторного анализа одного и того же контекста.
- В поручениях передавать пути к source of truth, точный вопрос и критерии, а
  не полные логи или дублирующиеся snapshots. Результаты с входными данными
  сохранять в `docs/`, когда они пригодятся повторно.
- Если один специалист расширяет typed configuration, до реализации
  downstream-модуля явно согласовать точные dataclass-поля, статусы и единицы.
  Downstream-код использует только этот контракт, без `getattr`-совместимости
  и альтернативных имён параметров.
- `independent-reviewer` вызывать после готового diff/артефакта и только в
  обязательных контрольных точках; `aircraft-lead` — только для реального
  междисциплинарного конфликта или системного решения.
- Не заменять инженерный контроль снижением модели: утверждённые модели и
  уровни effort обязательны для ролей. Полная политика:
  `docs/agent-token-policy.md`.

- `aircraft-lead` — главный инженер и интегратор; сводит междисциплинарные
  решения и финальное согласование.
- `aero-analyst` — аэродинамика.
- `structures-manufacturing` — прочность, материалы и технология изготовления.
- `cad-laser-engineer` — CadQuery, FreeCAD, DXF, SVG, STEP и STL.
- `avionics-autopilot` — ArduPilot, электроника, питание и failsafe.
- `independent-reviewer` — независимое инженерное ревью с findings, а не
  самостоятельное исправление проекта.

### Оркестрация и делегирование

Main использует специалистов и не пытается самостоятельно заменить всю команду
для сложных задач. Маршрутизация обязательна: аэродинамика, профиль, Reynolds,
скорость сваливания, CG и устойчивость → `aero-analyst`; нагрузки, карбон,
фанера, лонжерон, joiner, хвостовые балки, моторама и proof-test →
`structures-manufacturing`; CadQuery, FreeCAD, DXF, SVG, STEP, STL и
параметрические детали → `cad-laser-engineer`; ArduPilot, FC, GPS, Pitot,
ELRS, сервы, ESC, BEC, EMI и failsafe → `avionics-autopilot`;
междисциплинарные решения → `aircraft-lead`; независимая проверка →
`independent-reviewer`.

`independent-reviewer` обязателен перед release-to-manufacture критичных
деталей, после существенного изменения силовой схемы или геометрии, после
существенного изменения CG, после существенного изменения авионики/failsafe и
перед первым полётом. При конфликте CAD, расчётов и документации остановить
интеграцию и явно зафиксировать расхождение.

### Generated artifacts

`generated/` и `build/` — downstream-артефакты. После build проверять их diff
перед staging: изменения только в DXF timestamp, GUID, producer metadata или
порядке эквивалентных записей не являются инженерным изменением и не должны
попадать в commit. Содержательные изменения геометрии, размеров или manifest
должны иметь source diff и автоматическую проверку.
